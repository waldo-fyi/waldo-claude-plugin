## How to run

For each prompt:

1. **First pass — Claude Code (Desktop App).** Open fresh conversation in Claude Code in the Desktop App. Confirm `/model` is set to Opus 4.7 with adaptive thinking. Paste prompt verbatim. Single-turn unless Section B.
2. **Second pass — Claude Cowork (Desktop App).** Open fresh conversation in Claude Cowork in the same Desktop App. **Set model to Opus 4.7 from the picker; toggle adaptive thinking ON.** Paste the same prompt verbatim. Single-turn unless Section B.
3. **(Optional) Third pass — Claude Cowork at customer-default model.** If you want the model-version delta signal: re-run prompts A3, B (full 6-turn), and C2 on Cowork at **Opus 4.6 + adaptive ON** to check whether 4.6 (potential customer default) behaves differently from 4.7 on the same surface.
4. Capture both surface results in the per-prompt scorecard. If you ran the optional Opus 4.6 spot-check, note results in the run-notes section.

**At session start on each surface, run the sanity check:** ask Claude "What Waldo MCP tools and skills do you have available right now?" Confirm only lowercase `waldo` is active.

**Audience-parity framing (capture once per surface, not per prompt):**
- Was the prompt resolvable using natural language alone, or did the user need to invoke a slash command / explicit `load_skill`?
- This is the audience-parity signal. Business customers default to natural language; if natural-language routing fails, the experience is broken for them regardless of whether the same intent works via slash command.

## Routing rubric (same as Stage 1)

- **Pass** — Primary skill (first in `expected_skills`) fires (Claude Code: auto-trigger from description; Cowork: `load_skill` MCP call). No wrong skills fire. For `expected_skills: []`, no Waldo skill fires.
- **Partial** — Primary fires alongside a wrong skill, OR only a complementary fires.
- **Fail** — Wrong skill fires, no skill fires when one was expected, or any skill fires when none was expected.

## Surface-specific validation criteria

### Claude Code Desktop — what to capture per prompt

| Criterion | What to look for |
|---|---|
| Skill auto-trigger | Did a `waldo-fyi:*` skill load implicitly from description language, before any tool calls? |
| Pattern A-prime trail | Did a slash command name (`deep-dive`, `social-listening`, `ad-teardown`) appear in the tool trail alongside the skill? Single logical action, not double-invocation. |
| Description-driven routing | When asked "which skill did you use?", does Claude name the right one? |
| File-system persistence on truncation | If a tool returned an oversized payload, did Claude get a "saved to file" note? Did it re-read the file or proceed without? |
| Slash commands available | Type `/` — do `/waldo-fyi:*` commands appear in the autocomplete? (sanity check that the plugin loaded) |

### Claude Cowork (Desktop App) — what to capture per prompt

| Criterion | What to look for |
|---|---|
| Explicit `load_skill` invocation | Did Claude call the `load_skill` MCP tool? Which skill did it pass as argument? |
| Direct-tool competition | Did Claude bypass `load_skill` and go straight to `search_web` / `meta_advertiser_search` / etc.? |
| Anthropic platform-injected instruction | Was "use search before MCP tool" guidance visible in any system message or response framing? (Goody captured this in screenshots — it appears on Anthropic's Cowork / Claude.ai surface for new MCP connectors) |
| Native WebSearch firing | Did Claude use its built-in web search instead of the Waldo `search_web` tool / `web-research` skill path? |
| Truncation handling | If a tool output was oversized, what happened? (Cowork likely truncates server-side rather than persisting to file like CLI) |
| Slash commands | Should be ABSENT — confirm Claude doesn't reference any. |

### Audience-parity criteria (both surfaces)

| Criterion | What to look for |
|---|---|
| Natural-language sufficiency | Did the prompt verbatim trigger the right behavior, or did the user need to add reframing / explicit "use Waldo" language? |
| Citation format | Inline citations present, or stripped to a Sources section at end? Same intent across the two surfaces? |
| Brief clarification | On social/ad prompts, did Claude ask for timeframe / platforms / brand-or-topic before executing? Or skip clarification? |
| Multi-skill co-firing | When prompt clearly demands two skills (e.g., social AND ads), did both fire, or did Claude single-skill it? |
| Token-truncation disclosure | If a tool errored on size, did Claude disclose ("I couldn't read the full result") or proceed silently with claims? |

## Decision

The decision matrix below was framed before the run. With actual results in:

- Cowork is **NOT** materially worse than CC. On multi-turn retention and multi-skill firing, Cowork is *materially better* than CC.
- CC and Cowork both fail on the same 3 single-turn prompts (A1, A2, A3) — the routing-layer problem is real on both surfaces, not Cowork-specific.
- The platform-injection theory partially holds — A3 fails on Cowork as Goody documented — but A3 *also* fails on CC, so the platform injection isn't the sole cause.
- **The biggest story is Cowork's UX-friction layer (native docx, AskUserQuestion, search re-run, latency) on top of correct routing.** That's a different problem than the routing-only frame I built v0.3 priorities around.

→ **Refined v0.3 framing: routing fixes (items 1, 2, 4 from prior list) help both surfaces. But Cowork-specific UX-friction items become first-class v0.3 concerns, not afterthoughts.** See "Prioritized issue list" further down.

## Run notes (cross-cutting observations)

**Thinking-mode platform asymmetry (resolved 2026-05-06):** Adaptive thinking on Opus 4.7 is an **API-only parameter** (`thinking: {type: "adaptive"}`) and is NOT exposed in the Claude Code Desktop UI. Claude Code Desktop's effort dial (low / medium / high) is a different parameter. **`high` effort is the closest behavioral equivalent** to adaptive thinking ("Claude always thinks" — same behavior on complex tasks). The Claude Code Desktop pass at Opus 4.7 + High is therefore the closest analogue to Cowork's adaptive-thinking toggle that is achievable via the UI. No spot-check rerun needed — there is no truer match available without dropping to the SDK. Confounds dominated by surface mechanics (load_skill vs auto-trigger), not thinking-mode asymmetry.

### Cowork-only behaviors observed (none of these have a Claude Code analogue)

1. **Native `AskUserQuestion` tool fires upfront on some prompts** (A1, C1, C2, D1) with 3 user-answerable questions before any skill runs. Tool request signature: `{"query": "select:AskUserQuestion", "max_results": 1}`. **Open question:** is this triggered by a downstream Waldo skill needing brief clarification, or is it native Anthropic behavior? **If triggered by our skill body asking for clarification, we have redundancy** — the user answers AskUserQuestion natively, then our skill body asks for the same info again.

2. **Native `docx` skill auto-loads when the response shape suggests a document** (C1, C2). In a Linux sandbox the .docx creation **failed and fell back to writing markdown** — slow, frustrating, no warning to the user. **Mitigation candidate:** instruct skills to prefer our own document-writer skill, or add a guardrail in the skill body to say "produce inline response unless explicitly asked to create a Word document."

3. **Progress view in the right-hand menu** populated by native `Tasklist` / `Taskcreate` / `Taskupdate` tool calls. Lets user ask a question or recommend a change at a specific step. Power-user feature; most users won't discover it. Not relied-on by our flow.

4. **"Used Waldo integration" UI label** appears inconsistently — visible on A5, C2, D1, E1 but not on every other prompt. Unclear if visibility correlates with skill loading or is a UI heuristic. Investigate whether it's the customer-visible signal that the plugin actually ran.

5. **Tool approval gating affects latency.** When the connector is set to ask-permission rather than always-allow, tool calls may be sequentially approved, slowing the response. Investigate whether this is the dominant cause of Cowork's slower response time vs CC.

6. **Search re-running on truncation** (E1) — Cowork chose to re-run `search_meta_ads` with a narrower date window rather than paginate the existing result. Wasteful for the user (extra credits). CC handled the same overflow via pagination — preferred behavior.

7. **`load_skill` invocation is visually opaque.** UI shows "Running skill" but the actual `load_skill` MCP call isn't visible in the tool trail (C1, C2). Diagnostic blind spot for debugging routing.

8. **Tools persist across turns once loaded via ToolSearch** (B5) — once the deferred tool schemas are in context, the skill is not re-invoked on subsequent turns even when it should be. Means SKILL.md body guardrails (citation enforcement, brief clarification, etc.) only apply to the FIRST turn the skill loads on, not subsequent turns where the same tools are re-used directly.

9. **Citation naming style differs from Claude Code.** Cowork D1 used hyperlinked-keyword inline style (more like a blog post); CC used end-of-sentence citations with domain stubs (`reddit.com`, `x.com/Predictore_xyz`). Neither is ideal — post titles or content descriptions would be cleaner.

### Cross-surface observations

- **Cowork is slower than Claude Code overall**, attributable to: more tool calls per query, AskUserQuestion gate, native docx attempts, search re-runs, and possible tool-approval gating. **Strategy Agent web app is materially faster than Cowork on the same workload** — implies the slowness isn't inherent to MCP, it's the layering of native tools.

- **Brief clarification still skipped on social-intelligence prompts** in both surfaces (B3, D1, D2) even when the skill loaded — confirming Cherilyn's Stage 1 finding holds post-merge across surfaces.

- **Manual testing process was slow and laborious** (~1.5–2hr for 16 prompts × 2 surfaces). Need an automated or scaffolded testing approach for round 2.
